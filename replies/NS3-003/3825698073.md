An update from our side: we have closed https://gitlab.com/nsnam/ns-3-dev/-/merge_requests/2985 so that the fix for this issue continues in https://gitlab.com/nsnam/ns-3-dev/-/merge_requests/3011, by Srajan Gupta. We are not planning to carry merge requests to ns-3 ourselves; we will keep reporting, and testing fixes against our reproducer.

The closed merge request had three commits beyond the guard that both merge requests share. They are still readable there, and anyone is welcome to take them into nsnam/ns-3-dev!3011 or a follow-up:

- The root cause of the multi-interface case: DSDV advertises only `GetAddress (1, 0)`, so a node's other interfaces are never announced and its neighbours' next hops never resolve. The commit advertises the address of the interface each message is sent from: https://gitlab.com/nsnam/ns-3-dev/-/merge_requests/2985/diffs?commit_id=13397fcaf7da96c95602a255f86dc901fc8eae32
- The error callback invoked when queued packets are dropped: https://gitlab.com/nsnam/ns-3-dev/-/merge_requests/2985/diffs?commit_id=70399d9ea32acb4288c9845649e4926a57607049
- A regression test on a multi-interface chain that checks packets are actually delivered, not only that nothing crashes: https://gitlab.com/nsnam/ns-3-dev/-/merge_requests/2985/diffs?commit_id=aead3416d4f14ffdfbf45a5f7efa66050212162e

With only the guard, multi-interface DSDV stops crashing but still delivers nothing on the reproducer in this issue.

We will run nsnam/ns-3-dev!3011, in either form, against that reproducer once it is rebased (it currently has merge conflicts), and post the result here. Our record of the bug is https://github.com/swarm-routing/sim-tools/issues/240.
