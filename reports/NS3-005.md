# aodv: route lifetime overflows int64 when an interface comes up after t=0

**Modules:** aodv (`RoutingTableEntry`'s constructor and `SetLifeTime`; the callers in `RoutingProtocol`: `SetIpv4`, `NotifyInterfaceUp`, `NotifyAddAddress`, `NotifyRemoveAddress`), seen through core (`Time::operator+`). **Version:** ns-3.49 and `master` (`d07400baf45375afe6311d996ddc498722114f6d`, 2026-11-25), and earlier: the unchecked add is in every release read back to ns-3.7 (`aodv-rtable.{cc,h}` are byte-identical from ns-3.44 to `master`).

**Description.** AODV gives the routes that must never expire (the loopback route and each interface's local broadcast route) the lifetime `Simulator::GetMaximumSimulationTime()`, the largest `Time` (`INT64_MAX` ticks). `aodv::RoutingTableEntry` stores an absolute expiry, `lifetime + Simulator::Now()`, with no check (`src/aodv/model/aodv-rtable.cc:49`; `SetLifeTime` does the same, `src/aodv/model/aodv-rtable.h:258`). Creating such a route at any time after t=0 therefore overflows a signed 64-bit integer: undefined behaviour, which a build with `--enable-sanitizers` (UBSan, `-fno-sanitize-recover=all`) turns into an abort:

```
nstime.h:942: runtime error: signed integer overflow: 9223372036854775807 + 35000000000 cannot be represented in type 'long int'
#0 ns3::operator+(ns3::Time const&, ns3::Time const&) src/core/model/nstime.h:942
#1 ns3::aodv::RoutingTableEntry::RoutingTableEntry(...) src/aodv/model/aodv-rtable.cc:49
#2 ns3::aodv::RoutingProtocol::NotifyInterfaceUp(unsigned int) src/aodv/model/aodv-routing-protocol.cc:764
#3 ns3::Ipv4L3Protocol::SetUp(unsigned int) src/internet/model/ipv4-l3-protocol.cc:1336
```

(ns-3.49 line numbers.) The same lifetime is passed for the loopback route in `SetIpv4` (`aodv-routing-protocol.cc:714`) and for the broadcast route in `NotifyAddAddress` (`:886`) and `NotifyRemoveAddress` (`:951`).

**Why it is not seen in ordinary runs.** All four calls run at t=0 there (`SetIpv4` when the stack is installed, `NotifyInterfaceUp` when addresses are assigned, both before `Simulator::Run()`), so `Now()` is 0 and `INT64_MAX + 0` fits. Only an interface that comes up, or an address that changes, after t=0 reaches the overflow (a restart, a late `Ipv4::SetUp`, an address added later, a stack installed during the run). No AODV test or example calls `SetUp`, `SetDown` or `AddAddress` (read: `src/aodv/test/`, `src/aodv/examples/`, ns-3.49), so ns-3's own suites never take that path. Without sanitizers the wrap is silently undone by the next subtraction, `GetLifeTime()` and `Print()` return `m_lifeTime - Simulator::Now()` (`aodv-rtable.h:267`, `aodv-rtable.cc:185`), so the route looks alive and `RoutingTable::Purge` keeps it (the debug build prints the broadcast route as `UP +9.2e+09s`): two undefined operations that cancel at `-O0` on today's compiler.

**How to reproduce.** Two nodes on a CSMA link, stock AODV (`AodvHelper` defaults), stock ns-3 models only (core, network, internet, csma, aodv). At 1 s node 1's CSMA interface is set down (`Ipv4::SetDown`), at 35 s up again (`Ipv4::SetUp`, so AODV gets `NotifyInterfaceUp`); at 36 s node 1's AODV routing table is printed and the run ends. Default seed; the overflow does not depend on it. The program: https://github.com/swarm-routing/sim-tools/blob/1b36c739e0374295fc961772c044ecf90fb1b619/ns3/patches/NS3-005/aodv-lifetime-overflow.cc

curl -fsSL -o scratch/aodv-lifetime-overflow.cc https://raw.githubusercontent.com/swarm-routing/sim-tools/1b36c739e0374295fc961772c044ecf90fb1b619/ns3/patches/NS3-005/aodv-lifetime-overflow.cc

**Root cause.** `RoutingTableEntry` has no notion of an infinite lifetime: it keeps one signed absolute time and every setter adds `Now()` unchecked, while its callers spell "never expires" as the largest representable time. Both date from when AODV entered ns-3 (ns-3.7, 2010, `src/routing/aodv/aodv-rtable.cc:48`), when AODV routes were only created at t=0 in practice. `NotifyInterfaceUp` passes the lifetime at `aodv-routing-protocol.cc:764`:

```cpp
    RoutingTableEntry rt(/*dev=*/dev,
                         /*dst=*/iface.GetBroadcast(),
                         /*vSeqNo=*/true,
                         /*seqNo=*/0,
                         /*iface=*/iface,
                         /*hops=*/1,
                         /*nextHop=*/iface.GetBroadcast(),
                         /*lifetime=*/Simulator::GetMaximumSimulationTime());
    m_routingTable.AddRoute(rt);
```

and the constructor (`aodv-rtable.cc:49`) adds `Now()`:

```cpp
      m_lifeTime(lifetime + Simulator::Now()),
```

Elsewhere, read on ns-3.49: DSDV passes the same maximum lifetime (`src/dsdv/model/dsdv-routing-protocol.cc:982`, `1016`, `1076`) but its `RoutingTableEntry` stores it as given (`m_lifeTime(lifetime)`, `dsdv-rtable.cc:44`), so nothing overflows. No other `Simulator::GetMaximumSimulationTime()` or `Time::Max()` in `src/` is added to `Now()`. AODV's `RoutingTableEntry::Invalidate` adds the `DeletePeriod`-derived `badLinkLifetime` to `Now()` unchecked (`aodv-rtable.cc:165`); it overflows only for an attribute value near `INT64_MAX`, so the patch leaves it.

**Proposed fix.** `SetLifeTime` saturates at `Simulator::GetMaximumSimulationTime()`, and the constructor sets its lifetime through `SetLifeTime` instead of its own add:

The patch file: https://github.com/swarm-routing/sim-tools/blob/1b36c739e0374295fc961772c044ecf90fb1b619/ns3/patches/NS3-005/ns3-005-aodv-lifetime-saturate.patch. `maxTime - Now()` cannot overflow (`Now()` is never negative), and an expiry of `GetMaximumSimulationTime()` is the "never" its callers mean; every lifetime below the saturation point is unchanged, so no run without the bug moves. Fixing it in the entry, not at the four call sites, also covers any caller that passes a lifetime that large. Alternatives weighed: callers passing `GetMaximumSimulationTime() - Now()` (four edits, and the next caller repeats the bug); a separate "infinite" flag (more change than the defect needs). The patch applies cleanly to ns-3.44 to 3.49 and `master` `d07400ba`.

**Suggested test.** None of AODV's suites brings an interface down and up after t=0, so none can reach this path. A test under `src/aodv/test/` that builds two nodes on a CSMA link with AODV, calls `Ipv4::SetDown` at 1 s and `Ipv4::SetUp` at 35 s on one node's interface, and checks after `SetUp` that the interface's broadcast route is valid with `GetLifeTime()` greater than any finite lifetime would give (for example more than a year of simulated time) would fail under the sanitizers today and keep it fixed. The reproducer above is a starting point; `NotifyAddAddress` and `NotifyRemoveAddress` can be covered the same way with `Ipv4::AddAddress` and `RemoveAddress` after t=0.
