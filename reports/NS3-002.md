# AODV and DSDV: per-interface socket maps keyed by Ptr<Socket> make multi-interface runs depend on heap layout

**Modules:** aodv, dsdv. **Version:** ns-3.49 and `master` (`8ec9b4a190b52dadb5a3c35572dec687e1b75379`, 2026-11-11), and earlier: the same declarations are in ns-3.42 and ns-3.48.

**Description.** `aodv::RoutingProtocol::m_socketAddresses` and `m_socketSubnetBroadcastAddresses` (`aodv-routing-protocol.h:256`, `:259`), and `dsdv::RoutingProtocol::m_socketAddresses` (`dsdv-routing-protocol.h:151`), are `std::map<Ptr<Socket>, Ipv4InterfaceAddress>`. A map keyed by `Ptr` is ordered by pointer value, that is by heap address.

- AODV iterates `m_socketAddresses` and draws one jitter (`m_uniformRandomVariable->GetInteger(0, 10)`) per socket inside the loop when it sends a RREQ (`SendRequest`, `aodv-routing-protocol.cc:1123`, `:1150`), forwards one (`RecvRequest`, `:1490`, `:1512`) and sends a hello (`SendHello`, `:1984`, `:2011`). `SendRerrWhenNoRouteToForward` (`:2129`) iterates the same map and sends in map order without a draw.
- DSDV iterates its map for every triggered and periodic update (`dsdv-routing-protocol.cc:820` `SendTriggeredUpdate`, `:902` `SendPeriodicUpdate`) and sends in map order; its timer jitter is drawn once, after the loop.

On a node with more than one interface, which interface receives which random draw, and the order of the sends, therefore depend on where the allocator placed each socket. Two runs with the same seed and RngRun give different results if anything allocated differently before the sockets were created (another simulation earlier in the same process, a different allocator, a different build of an unrelated library).

**How to reproduce.** Stock AODV on a 3x3 point-to-point torus (four interfaces per node), UDP traffic, fixed seed. Run it twice in one process with a few thousand heap allocations kept alive before the second `Simulator::Run()`. The second run's delay sum and transmitted-packet count differ (in our run: delay sum 3.7024096 vs 4.3779808 s, 2432 vs 2431 L3 transmissions). With the maps keyed by interface index, every run gives the same result. The same dependence shows on `master` `8ec9b4a1` and on ns-3.49, three tries each, in our test that runs stock AODV with a second, idle interface per node alone and after an arm that churns the heap: https://github.com/swarm-routing/ns3-tools/blob/bb2951e1d25eee3e5d5260927f6288a443fa4ee8/ns3/routing-bench/test/routing-bench-test-suite.cc (`ArmIsolationTest`).

**Expected.** A fixed seed and run number give the same result regardless of heap layout (the same guarantee single-interface runs already have).

**Proposed fix.** Key the maps by interface index, for example `std::map<uint32_t, std::pair<Ptr<Socket>, Ipv4InterfaceAddress>>`, or keep them in a container ordered by interface index, so iteration follows interface order. The send loops keep their bodies; the lookups by socket and by address (`FindSocketWithInterfaceAddress`, `FindSubnetBroadcastSocketWithInterfaceAddress`, `NotifyInterfaceDown`, `NotifyRemoveAddress`) become lookups by `ipv4->GetInterfaceForAddress(...)`. A smaller alternative with the same effect is a comparator that orders `Ptr<Socket>` by the bound interface index. We are happy to test a patch against our multi-interface case.

**Our records:** https://github.com/swarm-routing/ns3-tools/issues/239 (root cause analysis), https://github.com/swarm-routing/ns3-tools/issues/198 (where it was found).
