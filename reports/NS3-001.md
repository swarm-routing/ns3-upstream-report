# AODV livelocks at a single simulation instant: SendIcmpNoRoute answers ICMP errors and locally originated packets (RFC 1122 §3.2.2)

**ns-3 version:** ns-3.49 and `master` (reproduced on `8ec9b4a190b52dadb5a3c35572dec687e1b75379`, 2026-11-11); ns-3.48 is not affected.
**Modules:** internet (`Ipv4L3Protocol`, `Icmpv4L4Protocol`), aodv.
**Platform:** Ubuntu 24.04, gcc-13; profiles default, debug, release and debug with sanitizers all behave the same.

**Summary.** Since ns-3.49, `Ipv4L3Protocol::RouteInputError` calls the new `SendIcmpNoRoute` (nsnam/ns-3-dev#825, RFC 1812 §4.3.2.7) on every routing failure when IP forwarding is on. With AODV in a partitioned ad-hoc network, this creates an ICMP Destination Unreachable storm at one simulation instant. Simulated time never advances again, and the run never finishes. The same scenario finishes in 2–4 s on ns-3.48.

**Reproducer.** One self-contained program, stock models only, 158 lines (GPL-2.0-only): https://github.com/swarm-routing/ns3-containers/blob/c8334e8ccd38a4fa974f283b4964ab69a0102d73/test/fixtures/manet-canary/manet-canary.cc. Copy it to `scratch/manet-canary/manet-canary.cc`, then:

```
./ns3 configure --enable-examples --enable-modules="core;network;internet;wifi;mobility;applications;aodv;olsr;dsdv"
./ns3 build scratch/manet-canary/manet-canary
timeout 120 ./ns3 run "manet-canary --protocol=aodv --range=100"   # hangs on 3.49 and master
timeout 120 ./ns3 run "manet-canary --protocol=aodv --range=175"   # dense: finishes
timeout 120 ./ns3 run "manet-canary --protocol=olsr --range=100"   # other protocols: finish
```

Scenario:
- 16 nodes in a 500 m × 500 m area;
- 802.11b ad-hoc, `RangePropagationLossModel` with a 100 m range, so the network is partitioned;
- random waypoint mobility (speed ≤ 20 m/s, pause 120 s);
- 3 UDP CBR flows (64 kbps, 512-byte packets) starting at 1, 2 and 3 s;
- 60 s of simulated time.

| Run | ns-3.48 | ns-3.49 | `master` `8ec9b4a1` |
|---|---|---|---|
| aodv, range 100, RngRun 1 | finishes, 2 s | never finishes (killed at 120 s) | never finishes (killed at 120 s) |
| aodv, range 100, RngRun 2 | finishes, 4 s | never finishes | never finishes (killed at 60 s) |
| olsr / dsdv, range 100 | finish | finish | finish |
| aodv, range 175 (connected) | finishes | finishes | finishes |

`examples/routing/manet-routing-compare` with its defaults does not trigger it. The network must stay partitioned long enough for AODV's request queue to drop packets.

**What happens.**
- With `NS_LOG="Icmpv4L4Protocol=function|prefix_time"`, a 10 s run on `master` logged 2,456,656 `SendDestUnreach*` calls in 20 s of wall time, all at `+5.160000000s` (on 3.49: 1,284,336 calls, all at `+8.146253127s`).
- gdb attached to the hung process shows, repeating: `LoopbackNetDevice::Receive` → `Ipv4L3Protocol::Receive` → `aodv::RoutingProtocol::RouteInput` → `DeferredRouteOutput` → `aodv::RequestQueue::Enqueue` → `RequestQueue::Drop` → the error callback. The rest of the cycle is read from the source, not from the backtrace: the error callback reaches `Ipv4L3Protocol::RouteInputError` → `SendIcmpNoRoute` → `Icmpv4L4Protocol::SendDestUnreachNetwork` → `Ipv4L3Protocol::Send` → `aodv::RoutingProtocol::RouteOutput`, which has no route and defers the packet through loopback again.

The steps of the cycle:
1. A data packet has no route. AODV defers it through the loopback device into its request queue.
2. The queue is full, so a packet is dropped. AODV reports the drop through the `RouteInput` error callback, so `RouteInputError` runs.
3. The node forwards (`IpForward` is true, as ad-hoc routing needs), so `SendIcmpNoRoute` sends an ICMP net-unreachable to the source. It does this even when the source is this node, and even when the dropped packet is itself an ICMP error.
4. That ICMP error has no route either. AODV defers it through loopback into the same full queue, which drops another packet, back to step 2. Every step is immediate, so the scheduler never advances time.

**Why this is a bug, not AODV's.** RFC 1122 §3.2.2 (https://www.rfc-editor.org/rfc/rfc1122#section-3.2.2) and RFC 1812 §4.3.2.7 say an ICMP error message MUST NOT be sent in response to an ICMP error message, a datagram destined to a broadcast or multicast address, a non-initial fragment, or a datagram whose source address does not define a single host. `SendIcmpNoRoute` only checks `m_ipForward` and a multicast or broadcast destination. The ICMP-error rule alone breaks this cycle at step 3 for every packet after the first. Separately, and as an ns-3-specific proposal rather than an RFC rule: an error about a packet this node originated only ever comes back to this node, so it can be dropped too.

**Suggested fix** (in `SendIcmpNoRoute`, or in `Icmpv4L4Protocol::SendDestUnreach` so that every caller is covered):
- return without sending if the offending packet is an ICMP error: protocol 1 with type 3, 4, 5, 11 or 12 (RFC 1122 §3.2.2);
- return without sending for a non-initial fragment (fragment offset ≠ 0) (RFC 1122 §3.2.2);
- return without sending if `ipHeader.GetSource()` is `0.0.0.0` or not a single host (RFC 1122 §3.2.2);
- our proposal: return without sending if `ipHeader.GetSource()` is one of this node's own addresses.

With the first and the last guard, every chain above stops at step 3. We are happy to test a merge request against the reproducer.

**Impact.** Any AODV simulation where the network partitions long enough for the request queue to drop packets. Other request-queue-based models using the same error callback are likely affected (for example out-of-tree AOMDV).
